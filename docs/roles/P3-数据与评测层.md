### `ScriptedHuman` 为什么是全项目最关键的小东西

课程要求里有"需要人工确认的任务"（场景 5）。但**评测必须能无人跑**，否则带审批的任务没法进批量测试，完成率指标直接废一半。

有了 `ScriptedHuman`：
- 演示时用 P2 的真 CLI（人来点）
- 跑批时换成 `ScriptedHuman`（按 YAML 自动答"批准"或"拒绝"）

同一个接口，两种实现。**这就是接口抽象的真正价值，答辩时值得单独讲一页。**

## 三、指标口径建议写清楚（否则数字站不住）

| 指标 | 定义 | 为什么这么定 |
| --- | --- | --- |
| **Task Completion Rate** | 通过 `TaskNode.acceptance[]` 全部检查项的任务数 ÷ 总任务数 | 不能靠人主观判断"算不算完成"。验收项必须是机器可判的：测试通过、文件存在、内容断言 |
| **Execution Time** | 从 `submit` 到终态的墙钟时间，**并拆成三段**：LLM 推理 / 工具执行 / 等待人类 | 只报总时长没有诊断价值；拆开后能说明瓶颈在哪 |
| **Token 成本** | 输入 + 输出 token 数 | 我们自己加的，多 Agent 系统成本失控是真实问题 |

另外：**每个任务至少跑 3 次**，报告里给均值 ± 方差。LLM 有随机性，跑一次就下结论会被问住。

## 四、实现约定

1. `query(task_id)` 必须按时间升序，且能重建出 span 父子树。
2. `search` 必须**按 namespace 隔离**——A Agent 的记忆不能被 B 搜到（这是"每个 Agent 独立记忆"的证据）。
3. `runner` 必须能**强杀超时任务**，不能一个死循环把整批跑挂。
4. 指标口径写进 `docs/metrics.md`，代码和文档必须一致。
5. 评测结果必须落到 `runs/<eval_id>/` 下可追溯，不能只 print 到终端。

## 五、验收标准

一条命令跑通三件事：

```bash
make eval        # 跑 15 道题，出完成率 / 耗时 / token
make report      # 生成 Markdown 报告 + 图
make ablation    # 记忆 on/off、并行 on/off 四组对比
```

以及：`runs/` 下的结果能被 P2 的 `replay` 直接读。
