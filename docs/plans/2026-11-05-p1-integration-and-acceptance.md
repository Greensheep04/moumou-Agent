## 2. 优先顺序与范围

建议路线：先交接审查，再接入正式评测，接着做外部服务实调和真实模型联调，最后整理演示与报告证据。

可选路线是立即做 Docker 隔离或重构异步工作区。这两项能够扩展能力，但会增加环境、接口和调试成本；当前缺口主要是现有功能尚未进入完整验收，建议放到本轮验收结束之后。

本轮约束：

- P1 负责 sandbox、workspace、tools 及其测试和接入示例；不接管模型决策、交互界面、完整评测题库或指标算法。
- 正式评测入口归 P3；涉及 runner/CLI 的改动由 P1 提供接入方案，与 P3 协调实现和合并。
- 保留现有工具名、契约字段、审批策略和 Engine 默认行为。
- 模型联调使用课程允许的 DeepSeek/HKGAI，由 P0/P3 负责模型与预算配置。
- 使用已有项目专用环境；路径通过配置传入，不在通用代码中写入本机绝对路径。
- 密钥留在本地环境或被忽略的配置文件，日志仅保存必要的验收结果。
- 分支、提交和 PR 使用项目功能描述，保留真实作者信息和实际开发历史。

## 5. 五项重点风险与对应检查

1. 只看到评测成功，却仍运行 LocalDirs：阶段 2 断言实际 Provider、worktree 和 Git 交付记录。
2. setup 导致父工作区不干净或子任务看不到初始代码：阶段 2 使用已提交 seed，并为调试题增加回归。
3. 多次评测互相污染：阶段 2 检查 repeat 独立，阶段 4 每批使用新输出目录。
4. 开发者能 push，却把工具审批链路当作已验证：阶段 3 分别记录真实批准、拒绝和人工交互证据。
5. 同步 Git 操作影响整体调度：阶段 4 先记录小样本工具与整合耗时；若出现可复现的明显阻塞，再与 P0 讨论异步接口，避免预先重构。
